# v0.8 当前接口与接入规范

## 1. 两个入口，避免把 Node 模块打进小游戏

离线生成/研究使用 `require('./src')`，需要 Node 22；微信或普通浏览器只使用 `runtime.js`，其依赖为 `layout.js`、`schema.js`、`content-hash.js`，四个文件均不依赖 Node、DOM 或 wx。

```javascript
// Node 离线工具
const E = require('./src');
const generated = E.generateDeal({
  layout: E.makeFixtureLayout(270),
  quotas: Object.fromEntries(Array.from({length: 15}, (_, i) => [`T${String(i).padStart(2, '0')}`, 18])),
  seed: E.seedFromText('my-level-seed'),
  targetOccupancy: 5,
  mutationAttempts: 0,
});
const verdict = E.verifyRelease(generated.deal, generated.receipt);
if (!verdict.ok) throw new Error(verdict.code);
```

`targetOccupancy` 是生成时保留路线的偏好，不是关卡必需容量，不是玩家新增难度选项。
`generateDeal` 输出对应的有解证据，不保证任意操作后仍有解。

```javascript
// 游戏运行端：应用自行管理对局编号；相同对局保存时保留该编号。
const {createRound, legalMoves, pick, shuffleRemaining} = require('./engine/runtime');
let state = createRound(deal, {roundId: '由应用或服务端生成的本局编号'});
const result = pick(state, legalMoves(state)[0]);
if (result.ok) state = result.state;
```

`createRound` 接受初始完整牌池，**不是载入 savedState 的接口**。无 roundId 时设为 null，表示未绑定会话；不能作为跨用户唯一编号使用。

## 2. 初始快照契约

`schema` 必须是 `astra-deal-1`；`dealId`、`layoutId` 为非空字符串；`slotCapacity` 固定为 7；`cells` 含 1..3000 个不重复 ID。
每格含有效 zone、整型矩形、图案字符串。矩形宽高必须正数，各分量绝对值不超过 1,000,000。
board 含安全整数 z；side 含非空 stackId 和从 0 连续的 position。同层相交、跨区相交、不同侧堆相交均被拒绝。
每种图案数量必须是三的倍数。不是只检查总牌数。
`origin` 可省略，提供时必须是非空字符串。`snapshotHash` 可省略以兼容旧版；提供时必须与实际内容一致。

所有公开加载/验解/求解入口使用统一基础结构契约。`validateSnapshotFields` 只检查基本结构、数量和可选摘要，不单独证明几何合法、初局有解或可以正式上线。
`validateLayout` 补充运行端几何检查；`replay` 用独立几何算法和列表三消检查操作。

## 3. 验解与发布门禁

### replay(deal, witness, options?)

返回 `{ok, code, ...}`。数据坏、操作非法、满槽失败、路径缺失等返回 ok=false。
`options.capacity` 仅供离线求解研究，可用 3..7 等分析值；deal.slotCapacity 仍必须是 7。
`VERIFIED` 表示该快照和路径在指定分析容量下通过；不是官方还原认证。

### verifyRelease(deal, receipt)

离线组合入口：
1. 通过真实 `createRound` 的输入检查。
2. 校验 receipt 的 witness 和 `dealHash`。
3. 使用完整快照 JSON 摘要核对配套凭据。
4. 独立回放整条通关路线。
5. 返回 `READY_FOR_ALGORITHM_RUNTIME` 及快照摘要。

失败时返回 `{ok:false, code, ...}`，不会用生成器自己提供的 verification 字段替代重放。
`tools/verify.js` 和 `tools/build-probe.js` 均使用此门禁。错误关卡或凭据在生成联调文件前被拒绝。
“READY”只面向本算法子包，不包含版号、广告、账号、真机或正式产品发布审批。

## 4. 标识分工：不要把不同含义混为一个 ID

|字段|含义|随取牌变化|随洗牌变化|
|---|---|---|---|
|state.originalDealId|这一局最初加载的关卡编号|否|否|
|state.roundId|会话层传入的对局编号；缺省 null|否|否|
|state.revision|本局已提交操作版本|是|是|
|state.shuffleOrdinal|本局已提交洗牌序号|否|是|
|state.deal.snapshotHash|当前不可变牌面和布局内容 SHA-256|否|牌面改变才变|
|state.deal.dealId|当前牌局/洗后产物编号|否|含根编号、序号及实际摘要|

`deal.snapshotHash` 不是当前整局状态摘要。槽顺序、taken、cleared 等不在其范围内；不得只靠它恢复对局。
建议会话日志同时保存对局编号、revision、完整实际牌面及命令。真正的存档恢复需按后续会话模块规范实现，不能把 `createRound(saved.deal)` 当成恢复至原进度。

哈希规范 `ASTRA_CONTENT_V1` 使用固定数组字段顺序：schema、layoutId、origin、slotCapacity，以及按原数组顺序逐张记录的 ID/图案/zone/矩形/z/stackId/position。
对象属性插入顺序不影响结果；cell 数组顺序参与结果。dealId、已有 hash、额外未参与玩法的元数据、私有 seed 和答案不参与。
同内容置换允许产出相同内容摘要；不为强制出现变化而偷偷再洗一次，但操作序号仍递增。

Portable SHA-256 为一致性工具，与 Node 的结果交叉核对；它不是密钥签名。拥有牌面的人也能重算它。

## 5. shuffleRemaining(state, rng)

rng 必须提供 `shuffle(array)`，返回原类型列表的置换。传入的是复制列表；结果出现增牌、漏牌、替换图案、错长度或非数组时抛出 `INVALID_SHUFFLE_PERMUTATION`，原状态不变。
只修改未取的主区/侧堆图案，不动已取图案、槽顺序、几何和清除数；不能在 LOST/WON 后调用作为复活。
返回新的不可变 deal 和新 state，保留 originalDealId/roundId。保存的是返回后的真实映射，而不是只保存“第几次洗牌”。
这仍然是社区参考下的候选规则，不因此成为原作已核实效果。

## 6. 与 v0.7 的兼容和测试迁移

旧版生成快照自带 schema、dealId、layoutId；无 snapshotHash 的 v0.7 快照可加载，并在内存新副本上计算摘要，原输入不修改。
旧 receipt 的 `dealHash` 按旧文件原内容检查，不要求用户先修改旧 JSON 再验解。
相同旧种子/布局/配额的牌面、dealId 和 witness 保持不变，新增 hash 字段会改变新 receipt 的完整 JSON 摘要。这是预期的文件格式增补。
任意自行改写图案或几何后携带旧摘要，会被拒绝。生成新的候选时须重新计算摘要、验证路径并生成对应凭据，不能简单把旧 VERIFIED 标志搬过来。

原测试中一个“七张不同牌导致失败”样例原本只有七张且没有配平；现在保留同样的前七次点击，追加余下同类牌使全局配平，仍断言第七步失败。
两个隐藏图案置换测试会为新合成世界重算内容摘要；另有专门的 stale-hash 测试保证正式入口拒绝旧摘要。

## 7. 后续接入范围

会话层使用 `pick` 结果驱动画面和状态；动画不得再次修改三消。正式应用的输入、奖励、计时、全道具、存档恢复及在线社交仍对应 v0.4 规范。
本版不新增体力、金币、玩家自选难度、作弊提示、实时对战或广告触发暗改底牌；历史隐藏参数未核实的部分仍单独标明，不能被本版测试通过自动“认证”。
