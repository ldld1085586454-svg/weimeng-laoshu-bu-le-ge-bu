日期：2026-09-18  
状态：算法设计与数学核验；尚非已实现的游戏工程。

## 0. 本次补的缺口与边界

v0.4 已定义状态、接口和守恒，但没有给出完整的关卡生产算法，不能把接口清单当成生成器。本稿补充生成、求解、难度评价、运行时结算及洗牌的具体步骤。

用户已授权：先找真实资料与社区实现；未取得原算法时，可以设计替代算法。本稿据此提出 **ASTRA_DEAL_V1（带通关证据的替代关卡生成器）**。这不是官方命名，不是原作源码，也不声称恢复了原作概率分布。

严格区分：

|类别|内容|是否属于原作事实|
|---|---|---|
|既有规则|七格槽、三张消除、遮挡、道具/地区/话题等已有范围|沿用 v0.3/v0.4 各规则证据等级|
|社区代码观察|批量造牌、随机打乱、不同洗牌方式|只说明对应仓库和提交怎么写|
|本次替代设计|合法取牌顺序＋安全图案序列＋独立回放|我方设计|
|本次替代设计的保证|初始牌局存在至少一条不使用道具的完整通关路径|不是对 2022 原作的断言|
|未恢复的原作参数|真实每日布局库、图案分布、重开分配、广告额度|不填猜测数字|

“有解”是我建议的替代生成器质量约束，不是悄悄把旧研究中的未决项改成历史定论。它不保证任意操作后仍然有解，不保证洗牌后可解，也不意味着应向玩家展示答案或难度选择。

### 三条实现路线的取舍

|路线|做法|优点|限制|
|---|---|---|---|
|纯随机后求解|数量配平、随机摆放，再搜索答案|生成逻辑短|可能大量候选无法在预算内证明；数量正确不等于可解|
|按同类批次叠放|同类成组构造，利用反向取牌顺序|便于构造一条简单答案|答案结构容易过于规律；不能直接还原真实难度|
|本稿推荐|固定布局约束，生成合法取牌路线和受控槽位序列，再独立验证|可证明初局有解，布局与图案可分开调|存在人为生成偏好，需实际试玩校准，不能称原算法复原|

下面给出第三条路线的精确定义，不继续把核心算法留给执行模型自由发挥。

## 2. 数据与前置条件

设主棋盘和侧堆共有 `N` 张牌，图案种类为 `K`。每类的初始数量为 `3*m[t]`，`m[t]` 为非负整数，至少一种为正；总数必须恰好满足 `N=sum(3*m[t])`。

这套替代生成器不要求每类数量相等。没有历史数量时，实验夹具可以使用等量分配，但不能把等量分配当成原版配置。固定布局牌数不匹配时拒绝输入，不能在屏幕外悄悄补牌。

输入：

- `LayoutTemplate`：稳定牌 ID、逻辑牌面矩形、明确层序、侧堆 ID 和取牌顺序；记录来源及版本。
- `PatternQuota`：每种图案的三张组数。
- `GenerationProfile`：压力偏好、候选预算、随机流版本；属于工具参数，不是玩家自选难度。
- `RuleProfile`：实际入槽/遮挡/侧堆规则版本。未绑定的规则不得靠生成器偷偷补齐。
- `EntropyRoot`：本次生成的随机根及算法版本；不使用当前时间作为每个函数的隐式输入。

输出分为两份：

1. `DealSnapshot`：实际布局、图案、区域和来源信息，交给游戏运行。
2. `GenerationReceipt`：使用的参数、完整候选身份、通关证据和难度报告，仅用于开发端/我方服务。

通关证据不是客户端提示功能。客户端如果持有完整底牌数据，仍可能被读取；不发送答案只能减少直接泄露，不能当成强防作弊。

## 3. AG01：确定性随机流与洗牌基元

### 3.1 版本化随机流

生成工作安排在开发电脑或我方服务，微信运行端优先加载已生成快照。下列是我方定义的可重放字节流格式，不声称它是原厂实现：

```
streamBlock(counter) = HMAC_SHA256(
    key = seed32Bytes,
    message = UTF8("ASTRA_DEAL_V1|" + streamName + "|") + uint64BE(counter)
)
```

计数从 0 开始；每块按大端拆成八个 32 位无符号数。`streamName` 固定为 `route`、`pattern`、`mutation`、`bot` 或 `shuffle`，加上候选序号，防止多插入一次随机调用就改变所有其他模块的结果。候选列表始终按稳定 ID 排序后抽样。

这是一种确定性伪随机取样约定；固定种子不是数学意义的真随机。真实运行保存最终结果和算法版本，不能只存 seed。开发比较必须在同一随机流规范下进行。

### 3.2 范围采样

对 `1 <= n < 2^32`：

```
limit = floor(2^32 / n) * n
重复读取 x = nextU32()
直到 x < limit
返回 x % n
```

拒绝采样用于避免直接取模引入额外范围偏差。循环达到工程上限 1,024 次时返回 `RNG_FAILURE`，不切换到取模捷径。这个上限是我方异常保护，不是玩法参数。

### 3.3 Fisher–Yates 置换

```
for i = length(a)-1 down to 1:
    j = uniformInt(i+1)
    swap(a[i], a[j])
```

在每步范围内均匀取样的前提下，每个带身份元素的排列概率相等。不能替换成 `sort(random-0.5)`，也不能每一步都从整个数组范围选交换对象。

本轮对三元素做穷举：全范围交换共有 27 个随机选择串，六种排列出现 4 或 5 次；上述逐步缩小范围共有 6 个选择串，六种排列各一次。该小例子用于检验算法差异，不是随机流的全面统计检测。

## 4. AG02：遮挡关系与侧堆约束

### 4.1 几何判定

对于上牌 A、下牌 B，逻辑矩形发生正面积重叠时才添加 `A -> B`：

```
A.left < B.right and A.right > B.left
and A.top < B.bottom and A.bottom > B.top
```

边缘恰好接触不算重叠。只用逻辑牌面，不含阴影、描边或动画缩放。所有坐标使用模板规定的整数逻辑单位。若模板不能确定上下顺序，返回输入错误，不凭数组遍历顺序猜。

检查所有较高牌，不只检查相邻一层。上层牌跨过中间空隙覆盖底层，仍应建立遮挡边。自环、重复边、环、非法矩形均拒绝。

同一侧堆若指定上到下 `s0,s1,s2`，建立 `s0->s1`、`s1->s2`。侧堆不是因为绘制偏移就允许玩家点中间牌。侧堆与主区的物理相交策略必须由模板和规则明确，不能自动混用两套判定。

### 4.2 更新

维护 `activeBlockerCount[id]` 和 `coveredByThis[id]`。取走 v 后，只递减它挡住的仍在原区域的牌的计数。计数为 0 的牌加入可取集合。撤回时按原始关系重新加入阻挡；洗牌仅换图案时不改几何图。

初始化朴素两两比较为 `O(N^2)`，更新一次为 `O(outDegree(v))`。先实现便于校验的版本；没有实测瓶颈，不提前引入复杂空间索引。

## 5. AG03：生成合法取牌路线

在只考虑遮挡、暂不考虑图案的图上，生成一个随机拓扑序：

```
frontier = 当前入度为0的全部牌，按ID排序
route = []
while frontier 非空:
    v = frontier[uniformInt(frontier.length)]
    将 v 从 frontier 移出，追加到 route
    对 v 的每条出边，递减目标入度
    将新出现的入度0牌加入 frontier，再稳定排序
assert route.length == N
```

如果没有取完却无可取牌，模板约束有环或输入不一致，拒绝，不补造一条不存在的路径。

随机选择前沿不产生“所有拓扑序等概率”的保证，本稿也不以此冒充原作分布。它只保证得到的顺序满足全部已定义取牌约束。第一版不使用复杂的均匀拓扑序采样。

## 6. AG04：生成不会自己走进满槽死局的图案序列

这是本稿的关键算法。

### 6.1 状态

- `r[t]`：还没有分配出去的图案 t 的数量，初始为 `3*m[t]`。
- `c[t]`：沿设计路线模拟取牌后，槽内 t 的数量，只能为 0、1、2。
- `q=sum(c[t])`：一次三消结算后的槽占用数。

选下一类 t 时：若 `c[t]==2`，第三张加入后立即三消，`qNext=q-2`；否则 `qNext=q+1`。

注意是**三消结算后的稳定槽数**，不能在临时达到七张时先判负。

### 6.2 安全候选条件

一个候选 t 必须同时满足：

1. `r[t] > 0`。
2. 更新后的 `qNext <= 6`。
3. 不能形成 `qNext==6` 且所有 `cNext[t]` 都小于 2 的状态，即六种不同单牌。

第三条不能遗漏：`A B C D E F` 虽然只有六张，但下一张至多凑一对，无法三消，必然进入七张无法消除的状态。这条约束只保护**生成器保留的通关路线**；玩家走错选出六种单牌仍正常失败，不自动替玩家救局。

### 6.3 伪代码

```
counts = [0]*K
remaining[t] = 3*groups[t]
word = []
for step in 0..N-1:
    candidates = []
    for t in 稳定图案顺序:
        if remaining[t] == 0: continue
        next = counts 的副本
        next[t] = (next[t] + 1) % 3
        qNext = sum(next)
        if qNext > 6: continue
        if qNext == 6 and max(next) < 2: continue
        candidates 加入 (t, next)

    assert candidates 非空
    使用正整数权重选择候选 (t, next)
    word 追加 t
    remaining[t] -= 1
    counts = next

assert sum(remaining) == 0 and sum(counts) == 0
```

压力偏好只改变候选权重，不能把所有可完成选择的权重设为 0。实验权重可用 `W=1+6-abs(qNext-target)`，其中 target 为 0—6 的整数；其结果始终至少为 1。不把这个工程偏好等同于真实通关率。

调试夹具的 target 可取 5，以检验高槽位压力。教学和每日关卡的正式参数尚需对照资料与试玩决定，不能把 target=5 发布为“原版第二关数值”。

### 6.4 为什么不会生成到一半无路可走？

始终有不变量 `(r[t]+c[t]) mod 3 == 0`。

- 如果存在 `c[t]==2`，该类型至少还剩一张，否则不变量不成立；选择它可三消，使槽数减少二，安全。
- 没有两张同类时，当前槽内都是单张。安全条件排除了六种单张，所以 `q<=5`。只要有一张单牌，选择同类下一张后最多 q=6，并形成一对；下一步即可取第三张消除。
- 若槽空且牌没有分配完，任选尚有余量的一类，得到一个单张，安全。

每一步剩余总数严格减少一，必在 N 步结束。结束时 r 全为零，结合不变量及 c 只能为 0、1、2，得到 c 全为零。这是一般情形的推理证明；有限穷举只用于检查实现该判定时有没有写错。

该证明不需要训练模型，也不需要指数级搜索。前提是图案配额合法、权重为正、图案状态独立于未定义道具，且使用七格三消规则。

## 7. AG05：将图案序列落到布局上

`pattern[route[i]] = word[i]`。

此时：

- route 保证每次取的牌符合主区遮挡和侧堆顺序；
- word 保证该条路线在七格三消规则下不失败；
- 终点所有牌取完且槽空。

因此至少存在一条不使用道具的解。**不是所有路径可解，不是唯一解，不是原作概率分布。**把图案赋回最终坐标后再验证，不能只验证中间数组。

一条 18 张的演算例：

```
图案：A B C D E A A B B C C D D E E F F F
槽数：1 2 3 4 5 6 4 5 3 4 2 3 1 2 0 1 2 0
```

六种图案各三张；第七步从六格放入第三个 A，结算后剩四格。此例只证明路径行为，不能据此说真人通关率很低。

`examples/` 中提供带主棋盘、两个侧堆和完整取牌顺序的合成例，不冒充历史关卡。

## 8. AG06：独立证据回放器

生成器的输出不能自行给自己盖“已验证”标记。

回放器从最终快照重新开始，以简单几何检查和侧堆首牌检查验证证据中的每步，不复用生成器维护的 frontier 或缓存入度数组。三消按实际牌 ID 处理，检查：

1. 每一步牌仍在声明来源区、当前可以取。
2. 不会同一张牌取两次，不会遗漏牌。
3. 先完成三消再判断满槽。
4. 主区、侧堆、槽和已消除区始终唯一归属、总数守恒。
5. 结束时所有牌已消除，槽、侧堆和主区为空。

证据包含 `dealHash + ruleProfileVersion + generatorVersion + route + traceDigest`。hash 用于一致性，不是客户端成绩可信的证明。

该验证的优化目标为 `O(N+E)`；独立朴素几何版可为 `O(N^2)`，先保留为对照真值实现。任何一步失败即拒绝候选，并报告第一处不一致，不能把后面“最终为空”作为通过理由。

## 9. AG07：有预算的求解器，而非“搜不到就无解”

生成器有保留路径，不需要求解器证明每个候选的基本可解性。求解器用于验证其他路线、残局及难度下界。

### 9.1 首版范围

`solveNoAssist` 只解决无道具规则下的主区＋侧堆＋槽状态。搜索态包含未取牌集合、图案计数和规则/图案版本；侧堆限制作为图约束。只有在不涉及道具、入槽顺序不改变后续可取资格时，槽可压缩为每类数量。

一旦涉及移出前三张、撤回或暂存顺序，槽的实际排列和相关历史不能丢掉。不能拿无道具压缩求解器证明包含道具的完整牌局。

### 9.2 返回三种明确结果

- `SOLVED`：附完整合法路径，须回放成功。
- `UNSOLVABLE`：在给定规则和完整搜索空间中，所有合法分支均已穷尽失败。
- `UNKNOWN`：达到节点/时间预算，未完成证明。

遇到非法输入另外返回 `INVALID_INPUT`，不混入上述结论。

### 9.3 搜索伪代码

```
DFS(state):
    if 全部完成: return SOLVED
    if 本次搜索预算耗尽: return UNKNOWN
    if state 在已证明失败缓存中: return UNSOLVABLE
    unknownSeen = false
    for action in 所有合法取牌动作（启发式仅改变顺序）:
        next = 无道具结算(state, action)
        if next 失败: continue
        result = DFS(next)
        if result == SOLVED: return SOLVED + action
        if result == UNKNOWN: unknownSeen = true
    if unknownSeen: return UNKNOWN
    写入已证明失败缓存
    return UNSOLVABLE
```

同图案不同位置可能释放不同底牌，不能简单合并成一种动作。启发式可以优先即时三消/释放更多牌，但不能因此丢掉其他合法分支。被预算截断的分支不能写入“无解”缓存。

最坏情况仍会指数增长；不能承诺任意大牌局都在固定时间内求解。首轮实验节点预算可定为 200,000，预算是工程配置，不是原作数值或性能实测。

## 10. AG08：难度分析，区分答案路线和玩家体验

### 10.1 保留一个指标向量，不先编一个“0.01%”

- `witnessPeak`：保留路线的最高稳定槽数。
- `witnessHighPressureRatio`：该路线中稳定槽数 >=5 的步骤比例。
- `unlockDepth`：模板遮挡链深度统计。
- `visibleChoiceCounts`：合法选牌数与能直接三消的候选数序列。
- `botResults`：指定可见信息和固定策略下的试验结果。
- `minPeakBound`：通过求解得到的全局最低峰值下/上界，未证明则保留 unknown。

**witnessPeak=6 不代表所有解都必须到六格。**要声称“最低也需要六格”，必须证明稳定槽上限为 5 时不存在任何无道具解，同时上限为 6 时存在解。限制容量求解只用于离线分析，不改变游戏的七格 UI。

### 10.2 不偷看底牌的模拟玩家

首版不训练强化学习模型。采用三个固定且可复现的策略：随机合法选择、优先三消/配对、带已见信息记忆的选择策略。

它们只接收 `VisibleBoard + VisibleHistory`，看不到完整底牌分配、保留答案和私有种子；若历史 UI 的部分遮挡可辨认规则未核实，测试档案显式标记采用“仅当前可取牌图案可见”的保守观察模型，而不冒充历史 UI。

不能让策略调用真实局面模拟未来分支再撤回，因为这可能提前读到未揭示底牌。需要预测时只能基于可见信息的假设分布；首版先不加入这类复杂预测。

防泄露检验：保持可见输入和随机种子相同，只更换不可见牌面，策略第一步选择必须相同。统计只报告在该策略、样本和观察模型下的成功次数/试验次数，不把机器人通过率写成真人通关率。

### 10.3 校准方法

固定一批布局和版本，采样多组候选，记录结构指标及模拟结果，再用真实试玩结果校准。不同日布局分开留出验证样本，避免只调好某一张图。

失败位置、重试和道具使用可用于观察体验，但不能把广告观看历史输入实时改牌逻辑。难度参数的发布只在新局生效；本稿不设计“看广告越多越难”或动态暗改底牌。

## 11. AG09：受约束的图案微调与候选筛选

为避免所有候选都带明显的生成顺序规律，可在同一布局中交换两张不同牌的图案，保持每类数量不变。

第一版每次交换后先回放原保留路线：失败则回滚；通过才计算质量指标。这样无需每次依赖复杂求解器，就能保持一个已知解。后续若允许改用新答案，则必须由求解器给出并经独立回放，不靠布尔值代替路径。

权衡：始终保留同一条路线会限制候选空间；不是均匀采样所有可解牌局。通过重采样 route 和 word 来增加候选多样性，不宣称与原厂分布一致。

我方工具首轮预算建议：最多 64 个初始候选，每个最多 64 次交换提案。目标质量区间作为显式输入；未提供区间时输出候选报告，不自行宣布哪一个等于原版难度。预算内没有命中时返回 `TARGET_NOT_MET`，不偷偷制造无解关或放宽已声明规则。

## 12. AG10：运行时取牌与三消

沿用 v0.4 `planPick -> commitAction`。设计路线、求解器都不能另写一套和运行时矛盾的三消规则。

```
校验来源和可取资格
从主区/指定侧堆首部/已绑定暂存位置取走牌
按绑定的槽序策略插入
若同图案达到3张，移除这3个ID并记入eliminated
更新允许撤回记录
若全部ID消除，结果WON
否则若稳定槽数==7，结果BLOCKED
否则结果PLAYING
验证唯一归属、图案引用和守恒，生成ActionPlan
```

同类相邻归组属于既有 R06 的候选行为，证据级别不因本稿改变。无道具生成证明只依赖“同类三个会消除”，不依赖视觉归组的具体插入索引。

快速点击、广告回调、动画回调都不能绕过唯一提交入口。动画结束不再次做三消，不决定是否加羊。

## 13. AG11：洗牌及其他道具的算法界限

### 13.1 洗牌候选 W1

为缺失的内部算法提供一套明确工作候选：保持几何、牌 ID 和侧堆次序不变，对主棋盘及未抽侧堆的图案多重集合做 Fisher–Yates 重排；槽与独立暂存区不参与。

这是**我方候选策略**，借鉴社区图案重排思路，但其区域边界不冒充原作已核实规则。与 v0.4 R20 策略绑定分开登记，不能静默覆盖正式配置。

执行流程：确定参与 ID 并排序 → 复制图案序列 → 置换 → 形成 ID 到新图案映射 → 检验参与集合与数量守恒 → 生成作用计划 → 由会话一次提交。

不强制重抽直到变成可解，不强制每次可见牌都变化。重复图案可能使一次合法置换看起来相同；除非取得原作依据，不擅自追加免费重洗。

只重排棋盘无法解决“槽已经七张且没有三消”的失败状态。因此这个算法不是复活算法，也不能保证救活任意残局。

### 13.2 移出、撤回、复活

移出沿用当前槽序的前三张，保留牌 ID 和来源，不删除牌。暂存可取顺序、少于三张时的效果与扣次继续沿用对应策略档案，不在算法中偷偷发明。

撤回恢复一笔被当前规则允许撤回的牌状态与几何阻挡；不回滚广告记录或已消耗凭据。社区“消除后清空撤回资格”的证据级别维持不变。

复活具体效果冲突没有被本轮解决。不要把生成器的“有解保护”拿来临时改牌复活，不擅自实现“移出＋洗牌”。未绑定效果继续只阻塞该操作，而非全部开发。

## 14. AG12：候选固化与结果重放

开发电脑/服务端生产并验收候选，微信端读取 `DealSnapshot`。不是每次点击实时调用生成器，也不依赖外部 AI API 判断牌能否消除。

关卡发布清单包含模板、算法、规则、图案分配和摘要版本。同一输入的可重放，不等于“历史原作同日重开一定同局”；每日/每次尝试如何选取候选继续由 R34 等分配策略决定。

我方结果验证应按本局快照、规则版本、实际随机决定和操作记录重放。广告资格另行验证；仅重放棋盘不能证明广告真的播放。开发端保留答案与线上结果验证是不同用途，不能仅因路径不同于保留答案就拒绝真实玩家的其他合法解。

## 15. 总生产流程与失败处理

```
读取有来源标识的布局与数量配置
    ↓
校验总量、坐标、遮挡、侧堆取牌限制
    ↓
AG03 生成合法取牌路线
    ↓
AG04 生成安全图案序列
    ↓
AG05 按路线分配到最终位置
    ↓
AG06 独立回放，失败即拒绝
    ↓
AG08/AG09 评价、微调、再回放
    ↓
生成带版本的DealSnapshot + 私有GenerationReceipt
    ↓
微信端执行既有玩法；不暴露答案、不新增玩法入口
```

失败代码：`INVALID_TEMPLATE`、`QUOTA_MISMATCH`、`CYCLIC_BLOCKERS`、`RNG_FAILURE`、`CERTIFICATE_REPLAY_FAILED`、`TARGET_NOT_MET`、`POLICY_UNRESOLVED`。异常时输出可定位问题，不用随机删牌、无限道具或跳关作为掩盖。
