## 2. 鱼了个鱼：可参考与不可移植

`genLevelRelation`维护砖块之间的覆盖关系；`doClickBlock`检查容量、状态与被覆盖关系，再把砖块加入槽中并统计三消。三消发生时将`opHistory`清空，随后按消除后的槽占用检查失败。这为R04、R07、R16提供工程对照。[C01]

`doShuffle`筛选未点击状态的块，打乱其图案序列再赋回。它可以支持R20的候选实现，但不证明原作也使用同一随机分布，不证明洗后必可解，也不能从仿作的状态分类直接认定原作暂存区是否参与。[C01]

页面将随机牌堆的首张绑定点击，提供了侧堆实现参考。但作者也加入了破坏、圣光、透视。README明确允许选难度、自定义图案、无限道具并不要求看广告。这些均属于仿作自身设计。[C01P,C01R]

没有把其撤回函数整体照搬：当前默认分支中可见撤回相关变动；历史版本中点击区和操作记录的处理也不能凭评论就判断完全正确。需要在我方内核对主堆、侧堆、暂存来源分别定义并测试。[C01,C01NOW]

## 3. xlegex：规则追踪

| 函数/文件 | 实际代码行为 | 对我方的意义 |
|---|---|---|
| `handleSelect` | 有两张同类时插入第三张，延迟后移除该组三张；其他情况加入槽中后检查是否7张 | 支持消除与满槽分支分离；100毫秒是社区参数，不作为原作动画时长 |
| `handleSelect`三消回调 | 将`preNode`置空 | 支持消除后不恢复整组三消的社区候选 |
| `handleBack` | 使用`preNode`，还原牌状态并从槽中移走 | 只能参考最近未消除对象，不能声称覆盖原作全部撤回来源 |
| `handleRemove` | 少于3张直接返回；用3次`shift`取前三张，放入`removeList`；清空`preNode` | 移出前三张有历史文字支持；少于3张/清历史为社区边界，须分开标识 |
| `handleSelectRemove` | 暂存列表移除对应项，再调用普通取牌 | 提供重新入槽参考；原作是否可任意选暂存牌还未知 |
| `App.vue` | 只显示移出和回退；设三段关卡；`trap`显式为false | 不包含完整原作洗牌、复活、广告与社交系统，不能交付成原版完整工程 |

以上来自固定提交，不是README猜测。[C02,C02P]

## 4. 必须隔离的trap分支

`useGame.ts`内存在名为`trap`的开关。它启用且命中条件时，会在图案列表中删去最后一轮图案；由代码可推导，这会破坏每类图案原先的三倍数数量。与此同时，该提交的`App.vue`示例关卡与初始化均显式设置`trap: false`。[C02,C02P]

因此应同时保留两个事实：库内存在这个可选分支；所查示例页面并没有启用它。不能把“社区有trap”说成“原作故意删牌”，也不能误报此示例默认在坑玩家。我方不引入该分支。

## 5. 发现的测试关注点（不是已经证实的Bug报告）

xlegex把三消放在定时回调中执行，槽位和最近点击对象可能在回调前被其他操作修改；暂存取牌先从暂存列表删除，再交给普通取牌函数检查容量。代码静态阅读提示要测试并发输入和满槽下暂存取牌，但没有运行复现，不写成已确认故障。[C02]

两项目都依赖网页界面/框架，不能把Vue页面直接改个后缀称为微信原生项目。参考范围是规则处理方式与需防范的边界，既定技术路线不变。[C01P,C02P]
