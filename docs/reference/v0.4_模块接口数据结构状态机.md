# 《羊了个羊》2022 微信版：模块接口、数据结构与状态机 v0.4

编制日期：2026-09-18  
范围：2022 年爆火时期的微信版。开发方向：原生 JavaScript / Canvas，微信开发者工具。  
阶段：技术设计评审稿；不是已完成的游戏工程，也不是“历史规则全部核实”的冻结规格。

## 0. 本文如何使用

用户已确认目标历史版本，并允许在原作证据缺失时参考社区源码。本稿继承 v0.3 的 45 条 R 规则、16 组 P 页面状态和 36 个 Q 核验场景，没有改变它们的证据等级。[BASE]

本文中的模块名、字段、状态名、事务和接口是我方工程设计，不是对原厂内部代码的描述。内部正确性可以独立设计；玩家看到的规则和商业化条件仍必须对应 R 编号。使用自己的服务和平台配置，不连接原作服务器，不沿用原玩家数据。

阅读顺序：本稿 → `contracts/interface_catalog.json` → `contracts/core_contracts.schema.json` → `contracts/policy_registry.json` → `02_模块交付与验收入口_v0.4.md`。历史出处在 `baseline_v0_3/`，本轮平台依据在 `sources/source_index_v0.4.json`。

**两种验证分开：**工程验证回答“状态是否一致、请求是否去重”；历史验证回答“是否与 2022 原作行为相符”。前者通过不代表后者通过。本轮仅检查文档、数据结构和引用完整性，没有执行游戏逻辑。

## 1. 总体组织：十个代码模块，不是十套系统

| 模块 | 建议目录 | 唯一职责 | 不允许越界的事项 |
|---|---|---|---|
| M00 公共契约 | contracts/ | 类型、规则来源、策略绑定、错误码 | 不能擅自为未知规则填写默认值 |
| M01 规则内核 | game/core/ | 取牌、入槽、三消、胜负、可取资格、守恒 | 不调用 wx，不操作动画和广告 |
| M02 关卡来源 | game/levels/ | 关卡快照、布局/图案/侧堆、来源校验 | 不把社区生成器说成官方生成器 |
| M03 道具效果 | game/assists/ | 生成移出/撤回/洗牌/复活变化计划 | 不自己发奖励、不直接扣商业额度 |
| M04 奖励流程 | game/rewards/ | 领取资格、渠道、观察结果、结算与去重 | 不因返回前台就发奖，不直接修改牌数组 |
| M05 会话调度 | game/session/ | 唯一状态提交者、生命周期、计时、快照 | 不按经验扩充玩家续局或暂停功能 |
| M06 页面表现 | game/ui/ | P01—P16 绘制、输入、动画、声音 | 不在动画回调里重新判胜负 |
| M07 微信适配 | game/platform/wechat/、open-data/ | 微信 API、好友开放数据域、平台错误归一 | 不导出好友列表来伪造自建好友榜 |
| M08 在线服务 | services/ | 日挑战、地区/话题/荣誉/装扮、结果结算 | 不新增实时匹配、聊天室或充值体系 |
| M09 对照验收 | tests/、tools/ | 合成样本、工程回归、历史对照 | 测试按钮/答案/模拟排行榜不能混入发布包 |

这是同一个项目内的目录和接口边界，不采用微服务拆分，也不需要十个独立部署。服务端可作为一个应用部署；存储供应商尚未锁定。

**依赖方向：**表现层提交意图 → M05 调度 → M01/M03 产生确定变化 → M05 提交 → 表现层消费结果。M04 通过端口调用 M07/M08；M01/M03 不导入平台实现。好友展示由 M07 的开放数据域承接，地区等我方业务数据由 M08 承接。[WX01]

## 2. 规则档案：让缺失证据只阻塞受影响部分

每局固定 `ruleProfileId + ruleProfileVersion + dealHash`。局中不因远程配置刷新改变撤回、复活或洗牌行为。切换策略仅发生在下一局，并有配置版本与来源记录。

`policy_registry.json` 保留全部 45 条规则。`production_strategy_id: null` 表示未绑定；不表示零次、无限次、不开发，或允许执行者自由选择。

| 信息类别 | 使用规则 |
|---|---|
| 已有历史依据 | 可以实现已经被支持的具体约束，不扩大至其未证实边界 |
| 社区候选 | 标出仓库/提交/函数；可在工程样本中对照，不自动成为正式配置 |
| 冲突或未决 | 对相关操作返回 `POLICY_UNRESOLVED`；其余独立模块照常设计与测试 |
| 工程要求 | 去重、守恒、校验等属于我方正确性，不作为原作历史事实 |

`POLICY_UNRESOLVED` 是开发诊断，不是新增给玩家看的道具文案。正式版本不能让玩家看完广告才发现效果没有绑定：领取预检查必须覆盖资格、效果、额度和平台能力。未完成的功能标为未通过验收，不通过删按钮假装已完整还原。

本轮没有把“所有关卡无道具可解”“洗牌必可解”作为约束；也没有引入社区的删牌 trap、自选难度、无限道具或三段连续关卡。[R21,R30,R31,R45]

## 3. 数据模型：同一张牌只有一个逻辑归属

### 3.1 DealSnapshot：这局实际使用的牌局

字段包括：

| 字段 | 含义与约束 |
|---|---|
| schemaVersion、dealId、dealHash | 数据版本、我方快照编号及规范化内容摘要 |
| provenance | 来源类型、证据编号、社区提交或采集说明；与可运行性分开 |
| layoutId、layoutVersion | 布局身份；不能只存一个“第二关” |
| patternAssignmentId | 图案分配身份；用于分开比较同日布局和图案是否相同 |
| tiles | 每张牌的稳定 tileId、初始图案、初始区域、几何布局引用 |
| boardGeometry | 逻辑牌面与渲染顺序；不采用网页 CSS 尺寸作为原作尺寸 |
| blockerEdges | 哪些仍在棋盘上的牌阻挡目标牌；没有自环、重复边或环 |
| sideStackDefinitions | 侧堆的初始有序 tileId；具体显示/取牌策略由配置提供 |

`provenance.kind` 只允许 `historical_capture`、`community_reconstruction`、`synthetic_test`。这些标记说明资料来源，不保证某个手工采集的完整性。`official_build_id` 仍为空；不得填入未取得的原版构建号。[R08,R09,R34,R45]

关卡快照应记录实际图案分配。随机种子只能辅助重放；没有算法版本和实际结果，不足以描述同一局。生成时是否保证有解、是否采用特殊概率仍未核定，不能由数据结构倒推。

### 3.2 RoundState：稳定局面

| 字段 | 含义 |
|---|---|
| roundId、revision | 我方对局编号；每次完整棋盘提交后修订号加一 |
| challengeId、periodKey、mode | 挑战身份、活动周期、教学/日挑战/话题挑战上下文 |
| ruleProfileId、ruleProfileVersion、dealId、dealHash | 绑定的规则和牌局快照 |
| status | CREATED、PLAYING、BLOCKED、WON、LOST、ABANDONED |
| zones.board | 仍在主棋盘的牌 ID |
| zones.sideStacks | 每个侧堆尚未取出的有序牌 ID |
| zones.tray | 槽中实际显示顺序；长度不超过 7 |
| zones.reserve | 移出后尚未消除的牌 ID；视觉排列与取回策略另绑定 |
| zones.eliminated | 已消除牌 ID，按批次日志追溯 |
| effectivePatternById | 当前图案；初始与快照一致，允许已绑定洗牌策略变换 |
| undoRecord | 上次可撤回操作的来源、ID、原索引/布局引用及有效条件 |
| roundUsage | 本局三道具与复活的领取/使用计数；与日广告记录分开 |
| appliedGrantIds | 已作用于此局的奖励凭据 ID |
| timingRef | 独立计时账本的引用；不把计时与棋盘动画合并 |

**唯一归属：**任一 tileId 恰好处于 board、某个 sideStack、tray、reserve、eliminated 中的一处。位置动画只是绘制插值，不是第六种牌归属。同牌不能既在暂存区又在槽中。

**守恒：**所有区域的 ID 集合并集等于初始 tileId 集合，交集为空。移出与撤回不能增减牌；洗牌保留总牌数及允许参与区域内的图案多重集合。是否有解不是这项检查的结论。[R44]

暂存区不在底层硬编码为“永久只能三张”。首次移出是三张，但复活后如何叠加仍待 R23；容量与可取顺序必须由对应规则决定，不把数据结构能力当作新增玩家容量。

### 3.3 三种修订号与三种身份不可混用

`round.revision` 只代表棋盘/道具作用后的稳定局面。奖励流程用 `reward.revision`；整个持久化包用 `commitSeq`。显示广告、记录生命周期不会把当前棋盘修订号意外改掉。

`roundId` 防止旧局回调污染新局；`commandId` 去重一次输入/提交；`rewardSessionId + grantId` 去重一次领取及其作用。服务器结果另有 `resultReceiptId`，不能混用。

### 3.4 UndoRecord 不是“还原整个应用”

记录 tileId、sourceZone、sourceStackId、sourceIndex、placementRef 和 `validAfterRevision`，只描述棋盘逆操作。即使恢复棋盘，也不能回滚已观看记录、日广告计数、已应用 grantId 或其他对局数据。[R15—R18,R43]

R16 的候选只说明三消后清掉撤回资格。R17、R18 未决时，不默认允许侧堆/暂存/跨道具撤回，也不把“记录了来源”误读成“所有来源都已获准撤回”。

## 4. 接口契约与错误处理

接口在 `contracts/interface_catalog.json` 中按 CT 编号登记。签名是语言无关契约，实际实现继续采用 JavaScript；不是要求改成 Vue 或 TypeScript 工程。

### 4.1 主要调用约定

- `createRound(context, deal, profile) -> RoundState`：校验该测试/运行用途所需的规则，创建稳定状态。
- `planPick(state, command, deal, profile) -> ActionPlan`：只规划选牌，不写状态，不调用随机数或系统时间。
- `planAssist(state, intent, grant, deal, profile, entropy) -> ActionPlan`：只规划作用；随机输入由调度器提供并记入重放材料。
- `commitAction(aggregate, command, plan) -> CommitResult`：唯一提交入口，同时提交棋盘变化、作用凭据和去重结果。
- `projectScene(aggregate, deal, viewProfile) -> SceneModel`：只输出应显示信息，不向调试外的界面泄露底牌。
- `prepareReward(aggregate, intent, capabilities, policy) -> RewardDecision`：领取前检查；没有可执行作用时不启动真实广告。
- `observeReward(aggregate, observation, policy) -> RewardDecision`：记录可观察的结果，区分已知完成与无证明返回。
- `createRoundResult(aggregate, receiptContext) -> RoundResultSubmission`：生成我方结算请求，不直接修改地区排名。
- `submitRoundResult(request) -> ResultReceipt`：我方服务返回已受理、拒绝或重试状态。

返回统一为 `OK`、`NO_CHANGE`、`REJECTED`、`BLOCKED_BY_POLICY`、`RETRYABLE` 之一，包含 `code、ruleIds、commandId、roundId、revision`。不用真假混合的 `success: true` 掩盖未执行操作。

错误码包括 `INVALID_STATE`、`TILE_NOT_AVAILABLE`、`SOURCE_MISMATCH`、`STALE_REVISION`、`COMMAND_ID_CONFLICT`、`POLICY_UNRESOLVED`、`QUOTA_UNRESOLVED`、`GRANT_NOT_VALID`、`GRANT_ALREADY_APPLIED`、`PLATFORM_UNAVAILABLE`、`UNVERIFIED_SHARE`、`STORAGE_FAILED`、`INVALID_SNAPSHOT`。

### 4.2 CommandEnvelope

所有有副作用的命令携带 `commandId、roundId、expectedRevision、type、payload`。同 ID 同载荷重复提交返回先前结果；同 ID 不同载荷必须报冲突。先查去重结果，再检查修订号，避免合法重试被错误判成过期。

输入里的 tileId 和 sourceZone 都要核实。客户端不能通过把一张被盖牌标为 `reserve` 绕开遮挡。已消除、已在槽内或来源不符的牌，返回不变状态。

### 4.3 ActionPlan

计划携带 `baseRoundRevision、inputStateHash、nextRoundState、semanticEvents、appliedGrantId、randomDecision`。提交时再次比对版本和输入摘要，验证 nextRoundState 守恒、槽容量、重复凭据与允许的状态转移。

摘要规范：对象键按字典序排序，数组顺序保留；UTF-8 JSON；只接受有限数值及安全整数计数；不接受 undefined、NaN、稀疏数组和运行时对象。SHA-256 用于一致性诊断，**不是防篡改证明**。客户端能改内容和摘要，因此服务端不能只验 hash 就相信成绩。


### 4.4 奖励阶段的提交与结算证据

`commitRewardDecision(aggregate, decision, observation) -> CommitResult` 是 CT25，由 M05 提交 PREPARED/OBSERVED/GRANTED 等奖励阶段和日广告观察。M04只返回决定，不持有可变全局状态。纯奖励阶段更新增加 commitSeq 与 reward.revision，不虚增棋盘 revision；真正作用到牌局仍由 CT08 同时提交 APPLIED 和新棋盘。

计数字段不能相加推算余额：reserved为当前有效预留，granted/applied分别为各阶段已发生次数，可能描述同一机会。扣次口径由对应R24/R26策略确定；策略未决不得以“limit减去三项之和”偷偷发明规则。

Grant另外绑定profileId/profileVersion/dealHash。标为server_verified时必须有实际verificationMethodId，不能只有客户端isEnded。结果请求除了operationEvidenceRef，还携带operationEvidence数组，每项含命令、相关凭据ID与随机决定；不能让服务端凭一个不存在的日志引用完成重放。

## 5. 棋盘状态机：逻辑状态与页面不要绑死

| 当前状态 | 事件/条件 | 新状态 | 说明 |
|---|---|---|---|
| CREATED | 关卡与必要策略校验通过 | PLAYING | 不代表一定已经有完整原作关卡 |
| PLAYING | 合法取牌后仍可继续 | PLAYING | 包括第七张触发三消后回到不足七张 |
| PLAYING | 结算后槽满且不能消除 | BLOCKED | 逻辑需要补救；弹窗顺序由 P09/R05 控制 |
| PLAYING | 所有牌已完成消除 | WON | 不能只看主棋盘空 |
| BLOCKED | 合法复活作用已提交并满足继续条件 | PLAYING | R23 未绑定时不能造出这个转移 |
| BLOCKED | 原作流程确认无补救或放弃补救 | LOST | 放弃确认的页面细节仍未核 |
| PLAYING/BLOCKED | 已确认的离局流程 | ABANDONED | 内部终态，不新增“放弃”按钮 |
| WON/LOST/ABANDONED | 再次挑战 | 新 roundId | 不复用旧局的奖励会话与修订号 |

`BLOCKED` 是内部状态名，不新增“卡关提示”页面。打开道具弹窗、广告界面或切后台，用独立的交互/生命周期状态记录，不自动修改棋盘输赢。

### 5.1 一次取牌的唯一结算顺序

校验命令与可取资格 → 从来源区移除 → 按 R06 绑定的槽序策略入槽 → 识别并消除三张同图案 → 更新撤回资格 → 判断全部清空或无法消除的满槽 → 生成事件 → M05 原子提交 → M06 播放动画。[R01—R10]

“原子提交”指我方内存状态一次更换，不是声称微信存储 API 提供数据库事务。落盘与网络结果另见第 8、9 节。

Q02 样本：槽内 A,A,B,C,D,E，点击可取 A。稳定结果为 B,C,D,E，消除三张 A，不输出失败事件。Q03 点击 F 则剩七张不可三消，输出 `RoundBlocked`。这些是已有规则的演示，不是本轮执行出的测试结果。

### 5.2 输入与动画边界

数据先稳定、画面按事件重现。M06 维护视觉牌位置和动画批次；命中测试基于当前画面及对应 tileId，不对尚未显露牌穿透点击。M05 每次执行前仍复核真实状态。

“整个动画期间都禁点”与“可以连续快速选牌”影响体验，未取得原作证据前不固定。通过 `inputDuringAnimationProfile` 局部实现；测试档案可以使用显式策略，但正式运行不得默默默认。动画完成只释放对应交互锁，不再次删牌/判胜/发奖。

切后台时可以终止绘制任务，逻辑仍是上一笔完整提交；返回是否续局由 R35 决定，不因内部能读快照就新增续玩功能。

## 6. 道具：作用与领取彻底分离

| 作用 | 本轮可以写清的约束 | 保留的策略点 |
|---|---|---|
| 移出 | 取槽内当前排列的前三张，移到暂存；牌数不变 [R11,R12] | 少于三张的按钮/扣次、暂存形态、取回顺序 [R13,R14] |
| 撤回 | 最近一次符合规则的点击返回来源位置 [R15] | 三消边界采用已登记候选；其他来源和跨道具仍未决 [R16—R18] |
| 洗牌 | 针对未使用牌；不承诺洗后通关 [R19,R21] | 位置/图案变换、暂存参与、随机分布 [R20] |
| 复活 | 单局一次工作基线 [R22] | 具体变化冲突未解 [R23]，禁止擅自“移出+洗牌” |

每种作用先生成计划，再由同一次提交记录使用次数与 grantId。M03 不能把“领取成功”写进用户状态；M04 也不能自己 shift 槽数组。

洗牌的实际随机置换必须记录在重放输入中；只存 `Math.random()` 被调用多少次不足以在不同环境重放。测试使用固定置换，不能据此推导原作概率。

对于复活：接口接受策略产出的完整 `nextRoundState`，但仍受守恒与状态机检查。仅仅打乱棋盘却让七张不可消除的槽保持原样，不能无条件将状态设回 PLAYING。未解决这种状态矛盾时，该策略不通过验收，不为迎合某篇文字描述硬写通关路径。

## 7. 奖励状态机：一次平台过程最多作用一次

### 7.1 三类数据分别存

`roundUsage` 记录本局各道具和复活的机会；`dailyAdLedger` 记录账户周期内广告观察；`rewardSessions` 记录某次申请、渠道、证据与作用。额度值和计数时点未证实时为未绑定策略，不用 null 当无限次。[R22,R24—R29]

### 7.2 一次 RewardSession 的阶段

PREPARED → PRESENTING → OBSERVED → GRANTED → APPLIED。

分支为 CANCELLED、FAILED、UNVERIFIED、STALE。进入 UNVERIFIED 表示缺少足够证据，不代表用户确定取消。任何终态的重复通知都不再次作用；同一会话不能同时归为成功和失败。

准备时固定 `roundId、expectedRoundRevision、purpose、channel、profileVersion、requestId、platformInstanceGeneration`。外部等待期间的交互限制与暂停表现由当前测试/运行配置决定。回调回来时核对对局和修订号；原局已结束则保留旧会话的审计状态，不将奖励改发新局，也不凭空创造通用道具库存。

### 7.3 平台事实与业务判断

所查官方接口定义中，激励视频关闭结果含 `isEnded`，用于区分是否完整观看；`show()` 调用完成不等于完整观看。[WX01] 我方将 `isEnded===true` 记为 `ad_completed_client_observed`，不是已获得服务端加密证明。

所查 `wx.shareAppMessage` 的参数类型没有 success/fail 回调且返回 void。[WX01] 因此接口不能虚构“分享成功 Promise”。适配器只汇报已拉起/返回前台等可观察事实；没有另行核验的合法证明来源，就将奖励判断保留 UNVERIFIED，不把后台停留几秒当原作规则，也不新增“好友点开后才领奖”的任务。

客户端观察本身可以被修改。防重复与防作弊是两件事：我方服务器可以去重申请和结算；不能仅凭客户端声称看完广告就宣称已实现强校验。可用的服务端广告验证能力尚未核验，不写成现成能力。

广告真实投放还需用户自己的平台配置。模拟成功/取消/失败只存在开发适配器，不能用于形成真实收入或对外榜单。

### 7.4 回调关联与崩溃边界

每个原生广告实例绑定明确的会话代际；注册与移除监听使用同一函数引用。[WX01] 不以“当前奖励会话全局变量”接收任意旧实例回调。迟到回调、重复 onClose、onError 后又 onClose 分别测试。

`APPLIED` 凭据与作用后的棋盘必须一起进入稳定聚合快照。跨进程的“最多一次”只能在凭据恢复或服务端核对基础上保证；存储被清除时不能假装本地去重依然成立。

退款、补偿或奖励转移不属于已确认原作范围。本稿只要求保留无法作用的旧局凭据与诊断，不自行新增邮件、补偿币或跨局道具仓库。

## 8. 会话聚合、保存与计时

### 8.1 SessionAggregate

持久化包包括 schemaVersion、commitSeq、round、rewardSessions、commandReceipts、timingLedger、resultSubmission 和 integrityHash。运行时 Canvas、音频对象、计时器、原生广告实例、微信授权秘密均不得序列化。

采用单一稳定聚合体而非几份彼此独立的散落缓存，避免“牌已移出但使用记录没保存”。实现上可用双槽写入：写较旧槽 → 校验 → 切换活动索引；读取两个合法包的最高 commitSeq。不能因此宣称文件系统完全耐断电或不可清理。

正常操作以内存提交为权威，异步落盘状态单独追踪；持久化失败必须记录并报告开发诊断，不能当成功保存。需要强持久性的奖励/结果提交还应查询我方服务凭据。恢复策略没有核定前，仅在测试中恢复稳定快照，不自动展示续局入口。[R35,R43]

### 8.2 计时账本

记录单调时钟的活动片段和排除片段、来源事件、可测质量。已确认只排除视频广告时间；其他弹窗、加载、分享、后台是否排除仍须对应策略。[R27]

排除区间按并集合并，不能因为广告同时触发后台事件而扣两次。`show` 被接受与实际视频开始可能有边界差异，记录观测精度，不把近似用时当原版逐帧计时。设备改时或进程重启后的断点单独标记，不能拿两个不同单调时钟直接相减。

周期归属由我方服务返回的 `periodKey、startsAt、endsAt、policyVersion` 表达；不是沿用开发电脑时区。具体历史刷新时区/截止规则未证实，配置仍待绑定，不写死某个时间点作为事实。

## 9. 在线数据：不做实时对战，但完整版本仍需要联网

地区羊群、话题、荣誉和装扮等沿用已确认范围。[R36—R42] 我方设计为一个在线服务及明确业务接口，不做对战房间、玩家帧同步或实时匹配。

| 操作 | 输入 | 返回 | 必须保留的边界 |
|---|---|---|---|
| bootstrap | 我方身份/客户端版本 | 时间周期、已绑定配置、数据版本 | 不泄露服务端凭据；未知规则不伪造默认值 |
| acquireChallenge | 模式、周期、请求 ID | 对局 ticket、牌局/配置引用 | 同日是否重用图案由 R34 策略决定 |
| submitRoundResult | ticket、roundId、结果、操作证据、用时质量、请求 ID | ResultReceipt | 同请求幂等；不能信任客户端单个“已赢”布尔值 |
| getRegionBoard | 周期、分页请求 | 带数据时点的地区展示项 | 去重人数/次数、并列仍由 R36 规则绑定 |
| getTopicView / getTopicOutcome | 活动和周期 | 话题、阵营、结果、领取状态 | 不从存在 PK 推导独立棋盘或新的玩法 |
| getHonors | 周期、荣誉类型 | 说明、获奖者/空缺、统计周期 | 不新增永久称号或额外礼包 |
| getWardrobe / equipOutfit | 目录版本/拥有形象 ID | 目录、拥有状态、已穿戴 ID | 不加入属性、付费购买或未授权装扮 |
| getPresetBarrage / sendPreset | 已登记的表达 ID | 原有表达及结果 | 不开放自由文本聊天作为默认实现 |

穿戴与预设表达由 CT26 `submitOnlineIntent(OnlineIntent)` 提交，分别校验拥有形象和预设ID。该写接口与 CT20 的只读查询分离；不增加自由聊天或额外奖励。

服务端验证完整操作可发现非法移牌，但不能仅据此证明真人操作、真实广告观看或真实用时；这些是不同的信任问题。源码重建的求解器也不自动证明原作难度分布。

**重复请求与重复通关分开：**网络重试同一个 roundId 必须只记账一次；同一个人新开第二局又通关是否再加羊，是 R36 的业务问题，不能用网络幂等规则擅自替代。

**好友单独走开放数据域：**主域发送展示请求与允许的布局参数；好友数据在开放数据域获取和绘制，主域使用其 sharedCanvas。[WX01] 不设计 `/getAllWechatFriends`，不把好友的原始头像/昵称列表回传给我方服务器。历史失败图标阈值及历史榜窗口仍需 R39，不用通用 score 排行榜填空。

**游戏圈：**封装平台原生按钮的创建、定位、显示/隐藏和销毁，不伪造一个 Canvas 按钮点击后直接调用不存在的“打开圈子成功”流程。[WX01]

## 10. 页面和资源契约

M06 负责所有 P01—P16，但资源和动态样式尚未完整取得。每组页面维护 viewState、可见入口、输入意图、资源 ID、证据 ID、未证实项与 mock 状态。加载/错误等工程状态不能伪称原版截图已经确认。

Canvas 布局的逻辑尺寸、缩放、安全区域和触摸坐标采用同一变换；具体原版尺寸与动画节奏留作素材测量结果，不能以示例的 375×667、40px 或 100ms 写成原作参数。

SceneModel 只包括目前允许可见的图案、层次、按钮状态、文案和动画事件。底牌仍可在内核和关卡中存在，但不能通过调试覆盖层或提示按钮泄露给玩家。测试日志不包含真实好友数据或广告平台凭据。

首页、棋盘、三道具弹窗、失败/复活、结果、话题、朋友记录、荣誉、换装、设置/弹幕/游戏圈都保留；开发先后不等于删除。[P01—P16]

## 11. 开发与验收门槛

第一门：45 个 R 编号均有主责模块、依赖、来源和 Q/E 场景映射；结构和示例通过静态检查。

第二门：在合成测试牌局上实现并执行内核/道具/奖励事务测试。候选策略的通过结果标为“候选行为通过”，不能升级历史等级。

第三门：P01—P16 逐组完成交互和平台异常验证；微信开发者工具与手机结果分别记录。

第四门：全部原作缺口有历史证据或被明确披露为重建差异，且广告、社交、素材使用及当前发布要求另行核验。没有满足这一门，不能称完整还原完成或可正式上线。

本轮没有新建可运行游戏，没有跑原作或社区游戏，也没有通过微信真机验收。可进入下一步的是按模块执行、补测和素材取证，而不是把文档打包结果当作上线成果。
